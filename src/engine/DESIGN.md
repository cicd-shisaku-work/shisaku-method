## 0. この文書は何か

本リポジトリの一部の文書（README、および長くなった原典）を、**モジュール群（正本）＋インデックス（並び）＋ビルド（組み立て）**の形に移す。その設計を、実装に着手できる粒度で定める。

対象の第一陣は二つ。

- `README.md`（日英併記）
- `concepts/human/shisaku-human-idion-structure/ja/shisaku-human-idion-structure.md`（節番号と本文中の節参照を持つ）

この二つは性質が違うので、両方が通れば仕組みの汎用性が一通り試される。以後の文書は、インデックスを一つ足すだけで載る。

## 1. なぜモジュール化するのか

根はひとつ——**この系の文書は完成しない**。版は `v0` を出ない（CONTRIBUTING §4）。記述が解釈であり、記述者の核が生きているかぎり更新されるからである。改訂が永続する系では、律速は書くことでなく**改訂の摩擦**であり、モジュール化はその摩擦を下げる構造である。分離それ自体が目的ではない。

摩擦の中身は五つに割れる。

### 1.1 監査が効く差分を作る

分業は、設計と裁定の側／実装と調査の側に分かれている。裁定する側は中身を通読せず、差分と提示で判断する。モノリスでは 1 節の改訂でも全文が動き、**差分が読めない＝裁定が降りない**。420 行の文書で 1 段落を直しても diff は全体になる。監査が働かない構造は、分業そのものを止める。

### 1.2 裁定の単位を物理にする

割る線は「**一塊として裁定される単位**」に引く。ファイルの都合ではなく判断の都合である。別々に裁定されるものが同じファイルにあると、裁定が束ねられて一度に答えられない。逆に、一緒に裁定されるものを割ると、関連管理の工数だけが増える（過分割）。**ただ分けることは目的でない——線が判断の単位でないなら、分割は失敗である。**

### 1.3 骨格を、文章でなく構造で担保する

規約は「語を消しても拘束が残る形」を目指す。骨格（序・命題・境界・接地・反証・倫理・新規性）を文章として規約に書くだけなら、守るかどうかは毎回の意志に依る。**ディレクトリと枠にすれば、埋まっていない枡が目に見える。** 族の原典で末尾の節が文書ごとに別の順に並んでいるのは、骨格が文章の中にしか無いからである。

### 1.4 正本を一意にする

版が冒頭と奥付に二重にある、同じ文書に複数の名がある、節番号が本文と参照の両方にある——いずれも**同じ事実が二か所にある**状態で、放置すれば必ず食い違う。メタをインデックスへ、参照を名前へ移すのは、整頓ではなく**二重化の除去**である。

### 1.5 生成側に渡す面積を構造で限定する

改訂のたびに文章生成の側へ全文を渡せば、そのたびに平坦化とすり替えの機会が生まれ、均された版が監査をすり抜けて残りうる。モジュール化は、作業面を「その単位だけ」に縛る檻である。**渡す面積を意志でなく構造で決める。**

## 2. 分けるだけでは壊れる（失敗機構と、塞ぐ四つの手）

**失敗機構：分割は、関係を構造へ移す一手とセットでなければ、部分最適化に落ちる。** 各モジュールは局所で正しく、全体で矛盾する。

ただし、関係が消えるのは分割のせいではない。モノリスでも関係は**散文の中に埋まっている**だけで、全体像は書き手の記憶にしかない（本文中の節参照が 45 行・78 か所あったことがその証拠で、節を 1 つ足せば全部が静かにずれる）。分割は、その関係を散文から構造へ移す機会である。移さなければ、作業面だけが小さくなって関係は散文に残る。

塞ぐ手は四つ。

1. **参照を構造として持ち、影響半径を引けるようにする。** 本文の参照をトークンにした時点で、参照は機械が読める関係になっている。あとは「このモジュールを参照している側」を引ければよい（`--refs`・§14）。運用規律は、直す前に影響半径を出し、参照している側と突き合わせること。機械が矛盾を判定するのではない——**裁定に上げる材料を機械が揃える**。
2. **通読の面を消さない。** 生成された全文は常に公開文書として存在する。モジュールは**編集の単位であって、読む単位ではない**。ここを取り違えると誰も通して読まなくなる。
3. **横断の検査を持つ。** 局所は正しいのに全体で矛盾する、を拾えるのは横断検査だけである（骨格の埋まっていない枡／用語の軸の衝突／二重定義／孤立モジュール）。
4. **分割線そのものを検算する。** 相互参照が密な二つのモジュールは、割ってはいけないものを割った疑いである。参照グラフから機械的に出せる。粒度の規準を、あとから実測で検算できる形にしておく。

## 3. 粒度と所属の導出

粒度と階層は、見た目でなく §1 の目的から導く。

### 3.1 粒度 ← §1.2

判別子は一問——**この節を直すとき、隣の節も同時に直すことになるか。** なるなら束ね、ならないなら割る。

実例：本書の第一陣では、ある節の 2 つの下位節が本文から独立に参照され、独立に改訂されていた → 割る。一方、各節の規則を集約した節は、節を直せば必ず一緒に動く → **独立の裁定単位ではない**（ゆえに、将来は各節から生成する候補になる）。

### 3.2 所属 ← §1.3

ディレクトリが表すのは**役**であって、位置ではない。役は四つ。

| 所属 | 役 | 何が入るか |
| :-- | :-- | :-- |
| `subject/` | **対象について** | 理論が語る対象の構造（命題・機構・その下位区分） |
| `application/` | **適用について** | どう使うか（用法条件・適用範囲・調整の指針）、どう測るか（観測手続き）、どう外れるか（誤用の型・倫理条項） |
| `document/` | **文書について** | この文書としての身分（意味＝兄弟との差・根拠＝接地・目的・目標・失敗機構＝反証条件・系の中での位置） |
| `canon/` | **原典について** | この文書が仕える原典の、接地（事例・証跡）・改訂候補（フィードバック）・圧縮の兆候（分離候補の観察） |

`canon/` は補足にだけ立つ（原典には、仕える原典が無い）。導出は本節の末尾に置く。

**三分の導出は二経路から来ている。**

- **六要件の再帰適用**：六要件（様式の正本は `authoring-policy.md`「原典の必須様式」の節）を対象の層と文書の層へ当てると、末尾の節（新規性・接地・反証条件・適用範囲・倫理）の正体が枡として現れる。ただし**用法条件の枡（適用範囲・倫理）は、対象の層にも文書の層にも読めて曖昧が残った**。
- **BOK との同型**：多人数の合意で編む知識体系が持つ部位（原理・テーラリング・測定・リスク・ステークホルダー）を突き合わせると、**「使う側」に関わる部位が欠けている**と出た。

二つの独立な経路が同じ場所を指したので、用法条件の系列を独立の役として立てる。

**実物で確認した（2026-09-12）。** KOSEI Mining 定義書の「警告：劇薬としての側面」「本概念の対象者」「求められる資質」、認知フレーム原典の「品質規律」「透明性の原則」「賞味期限の原則」は、対象についてでも文書についてでもない。役の二分では収まらない節が、既に実在している。

**位置と役を取り違えない。** 「序：この文書は何か」は位置が先頭なだけで、役は文書についての節（目的）である。題辞も読み方の宣言であり、文書についての節である。位置はインデックスの順序が持つ（§3.3）。

**四つ目（`canon/`）の導出も二経路から来ている。**

- **六要件の再帰適用（三層目）**：補足は層を三つ持つ——対象の層／この文書の層／**原典の層**。原典の層へ六要件を当てると枡が出る。根拠（原典の接地）・効果と失敗機構（原典が圧縮されている兆候）・目標（原典の改訂候補）。原典そのものには三層目が無いので、この枡は補足にしか現れない。
- **注釈体との同型**：法文に対する判例集、本文に対する注釈書は、本体の部位ではなく**本体について語る別体**として在り、本体を接地し、その改正を駆動する。同じ部位が、補足の中では節として現れる。

二つの独立な経路が同じ場所を指したので、原典について語る系列を独立の役として立てる。

**実物で確認した（2026-09-14）。** IDION 補足 4 本の 27 節のうち 6 節が三役に落ちない——`idion-cases.md`「事例集」「分離候補の観察欄」と、補足 4 本それぞれの「原典へのフィードバック候補」。決め手は、`idion-cost-forms.md`・`idion-axes-map.md`・`idion-system-isomorphism.md` が「原典へのフィードバック候補」と「失敗機構」を**同じ文書の中に両方持つ**ことである。同じ役なら衝突する。衝突していないのは、一方が原典の、他方がこの補足自身の失敗機構だからである。

**判別子は一問——その節が語っているのは、この文書の外にある原典か。** 語っているなら `canon/`。外れる例を三つ置く。`kosei-mining-origin.md` の「証跡」は自分の主張の出所であって、外に原典を持たない（`document/`）。`shtt-depth-terms.md`「境界検査の事例（実話でない・類型として）」は弁別子の当て方の見本である（`application/`）。補足の「位置づけ（原典／応用の線）」は、この文書が原典に対して持つ身分の宣言である（`document/`）。

### 3.3 順序と深さ ← §1.1 と、所属との分離

**所属はディレクトリ、順序と深さはインデックス。** 二つを同じ階層に背負わせない。こうすると、骨格の順序がまだ裁定されていなくても所属は切れる（裁定が降りたら、動くのはインデックスの 1 か所）。深さに数えるのは親子だけで、所属は数えない（§8 の `cluster_depth`）。

### 3.4 名前 ← §1.4

役の名をそのまま使い、短縮した別名を作らない（§6「名前は一つ」）。

### 3.5 所属にできるもの／できないもの

ディレクトリで表せる軸は何本もある——六要件そのもの／抽象度の層／読者の局面／成熟度／文書の部位／役。このうち**所属にできるのは、時間で動かない軸だけ**である。

**規準：id は参照の宛先である。ゆえに id を動かす軸を、ディレクトリにしてはならない。** 成熟度（確定・候補・未決）は裁定が降りれば動き、読者の局面は一つの節が複数に属する。どちらも**属性**（front-matter）で持ち、所属は役で決める。

役（対象について／適用について／文書について／原典について）が所属になるのは、役が時間で動かないからである。文書の部位（前付・本文・後付）は位置であって役でないので、所属にしない（位置はインデックスの順序が持つ）。

`canon/` もこの規準を通る。フィードバック候補が原典の条項として採られても、動くのは**原典側に新しいモジュールが立つ**ことであり、候補を挙げていた節は `canon/` に留まる。id は動かない。

## 4. 解決する課題と失敗機構

**目的：** 長い文書の編集を、局所の編集に変える。

現状で起きていること（実測）。

- README は 420 行。1 節の書き換えでも、ファイル全体が diff に載る。日英の対応がずれても、機械では気づけない。
- IDION 原典は 314 行で、本文中に「第N節」の参照が 45 か所ある。節を足す・並べ替えると、45 か所を手で追うことになる。
- README には `concepts/…` のパス言及が 18 か所、原典末尾には配置先を含む canonical URL がある。`concepts/` の配置はいずれ変わる予定であり、そのとき、ずれたことを検出する手段が今は無い。

**失敗機構（この設計が無い／守られないと何が壊れるか。分割そのものの失敗機構は §2）**

- 正本を二重に持つ（モジュールと生成物の両方を手で編集する）と、内容が食い違い、どちらが正しいか誰も言えなくなる。
- 番号・パスを字面で持ち続けると、参照は静かに腐る。読者にはリンク切れとして、著者には手戻りとして出る。
- 分割と同時に内容を編集すると、「どこまでが移動で、どこからが改訂か」が diff から読めなくなり、移行の正しさを検証できない。ゆえに分割の合格条件は、**組み立て結果が既存の公開文書とバイト一致すること**に置く（§9 の連結規約は、この関門を成立させるために存在する）。

## 5. 全体像

```
モジュール群（正本）  ──┐
インデックス（並び）  ──┼─→  ビルド  ─→  公開文書（生成物・直接編集しない）
パス対応表           ──┘
```

- **正本はモジュール。** 公開文書（`README.md` 等）は生成物であり、直接編集しない。
- **ディレクトリは所属を、インデックスは並びを表す。** 二つを混ぜない。
- **モジュールは自分がどこに置かれるかを知らない。** 見出しの深さ・節番号・参照先の番号は、組み立て時に決まる。これにより、並べ替えがモジュールの本文に触れずに済む。

ビルドは単一責任で分ける。

```
build.py（入口・司令塔）
  ├─ index      … インデックスの読み取り、並び・深さ・番号の決定
  ├─ module     … モジュールの読み取り（.md / .xml）とメタの正規化
  ├─ heading    … 見出しの深さシフトと番号の合成
  ├─ token      … 本文中トークンの解決
  ├─ assemble   … グループ連結・区切り線・末尾改行
  └─ lint       … 静的検査
```

```
│
└── docs/                      # 文書（正本モジュール）
    ├── root/                  # リポジトリ直下へ出る文書
    │   └── readme/
    │       ├── index.toml
    │       ├── common/        # この文書の中で言語を持たないモジュール
    │       ├── ja/
    │       └── en/
    └── concepts/              # concepts/ へ出る文書
        └── shisaku-human-idion-structure/
            ├── index.toml          # 原典
            ├── ja/
            └── supplements/        # この原典に帰属する文書
                ├── idion-axes-map/
                │   ├── index.toml
                │   └── ja/
                ├── idion-cases/
                ├── idion-cost-forms/
                └── idion-system-isomorphism/
```

**名前は一つ。** 文書の識別子は、出力されるファイルの語幹（＝概念ディレクトリ名）と一致させ、短縮した別名を作らない。書き方は英小文字とハイフン（リポジトリのディレクトリ命名に合わせる。`README.md` の識別子は `readme`）。モジュールのディレクトリ名・`[doc] id`・`paths.toml` のキーが、同じ一つの名を指す（`[doc] id` とディレクトリ名の一致は lint が見る）。別名を作ると、同じ文書に三つの名が付き、どれがどれかを覚える仕事が増える。

**文書の中は、所属（役）でディレクトリを切る。** その節がどの役に属するか（対象について／適用について／文書について／原典について）をディレクトリで表す。所属は深さに数えない（§8 の `cluster_depth`・§12）。順序は所属でなくインデックスが持つので、骨格の順序が後で変わっても、動くのはインデックスの 1 か所である。

**`docs/` の下は、出力先のトップ区分を写す**（ルート直下か `concepts/` か）。棚（射程）でなく出力先のトップなので、`concepts/` の中が再編されても、この区分は動かない。文書は 1 文書 1 ディレクトリで、`index.toml` を持つディレクトリがビルドの対象になる。

**補足は、仕える原典のディレクトリの中の `supplements/` に置く。** 補足は原典に帰属するものなので、置き場が帰属を表す。**走査は文書を見つけても降下を止めない**——止めると（`dirs[:] = []`）、原典の下に置いた補足が走査に掛からない。文書の識別子はディレクトリ名なので、入れ子にしても原典・補足とも名は変わらない。

出力先そのもの（階層とファイル名）はインデックスが持つ。配置が変わってもソースは動かない。

## 7. モジュール

### 7.1 二つの形式

同じ内容を、次のどちらでも書ける。読み取った直後に同じ内部表現（メタ＋Markdown 本文）へ正規化し、以降の工程は形式を知らない。

**Markdown 形式（`.md`）**

```markdown
---
id: strength/combination-rule
title: 累積の結合則
numbered: true
---
# 累積の結合則

本文…
```

**XML 形式（`.xml`）**

```xml
<module id="strength/combination-rule" title="累積の結合則" numbered="true">
  <body><![CDATA[
# 累積の結合則

本文…
]]></body>
</module>
```

- front-matter は `key: value` の平坦な行だけを許す。入れ子・リスト・複数行値は受け付けず、違反はエラーにする（黙って読み飛ばさない）。
- XML は標準ライブラリ（`xml.etree`）で厳密に読む。ルート要素は `module`、本文は `body` の CDATA。
- **CDATA の空白規約：** `<![CDATA[` の直後の改行 1 つと、`]]>` の直前の改行 1 つを取り除いた残りを本文とする。ここを決めておかないと、XML のモジュールでだけバイト一致が崩れる。
- **`]]>` の扱い：** 本文に `]]>` が現れるときは `]]]]><![CDATA[>` と分割して書く。生の `]]>` は lint がエラーにする（現時点の対象文書では 0 件）。
- どちらの形式を使うかの規則は持たない。形式は用途で選ぶ。

### 7.2 メタの項目（両形式で共通・これ以外は不許可）

| 項目 | 必須 | 意味 |
| :-- | :-- | :-- |
| `id` | ○ | モジュールの識別子。パスから導出されるものと一致すること |
| `title` | — | 見出しの題（番号を含まない）。省略時は本文の先頭 H1 の文字列を題とする |
| `numbered` | — | 節番号を付けるか（既定：インデックスの `[numbering] enabled`） |
| `raw` | — | `true` のとき、見出しのシフトと番号付けを行わず、本文をそのまま置く（冒頭・奥付など）。**トークンの解決は `raw` でも行う** |
| `maturity` | — | 成熟度（`pending` など）。**所属でなく属性**として持つ（§3.5）。出力には現れない。README のメタ `status`（リポジトリの状態）とは別の軸なので、語を分ける |
| `level` | — | 出力での先頭見出しのレベルを明示指定する（`1` なら `#`。既定：ブロックの `base_depth` と id の階層から導出） |

未知の項目はエラー。形式によって書ける項目が違うと、形式の選択が内容を縛るため、項目は一つの表に閉じる。

### 7.3 id と見出しの規約

- id ＝ 文書ディレクトリと言語ディレクトリを除いた相対パスから拡張子を落としたもの。`ja/strength/combination-rule.md` → `strength/combination-rule`。
- 階層はディレクトリで表す。言語は id に含めない（日英で同じ id が対になる）。
- **id は所属（役）を含む**（`subject/strength`・`document/scope`）。所属は深さに数えず、所属の下の入れ子だけが深さになる（`subject/strength/combination-rule` は深さ 2）。
- 同じ id の `.md` と `.xml` が同居していたらエラー。
- 本文の先頭見出しは常に H1（`#`）で書く。深さは組み立て時に与える。先頭が H1 でない、H1 が二つ以上ある、はエラー（`raw` を除く）。
- 子見出し（H2 以下）は、先頭 H1 と同じ量だけシフトする。
- コードフェンス（``` / ~~~）の内側の `#` は見出しとして扱わない。

### 7.4 共有モジュール（文書をまたぐ部品）

`src/shared/` に置くモジュールは、どの文書からも呼べる。インデックスでは `shared:` を付けて指す（`shared:license/cc-by-4.0`）。

- 文書ごとに変わる部分は `{{meta:…}}` で空けておき、**呼び出した文書の `[meta]` で埋める**。共有モジュール自身は値を持たない。
- 共有モジュールは、自分が要求するメタを front-matter で宣言する（`requires` / `optional`）。
- `[meta]` の値はトークンを含んでよい（`canonical = "{{url:shisaku-human-idion-structure}}"`）。解決は再帰で行い、深さの上限は 5、循環はエラー。
- 差し替えは、別の共有モジュールを置いて、そちらの id を呼ぶだけでよい（例：CC BY 4.0 以外のライセンス）。共有モジュールは文書に強制されない。

ライセンス表示がこれにあたる。実物を見ると、文書ごとに違うのは冒頭の一文と配置先 URL だけで、残りは同一である。

```markdown
# License

{{meta:license_intro}}

Copyright (c) {{meta:copyright_year}} shisaku

Licensed under the Creative Commons Attribution 4.0 International (CC BY 4.0).

License: https://creativecommons.org/licenses/by/4.0/
Author: https://note.com/abstraction
Canonical repository: {{meta:canonical}}
```

### 7.5 メタのテンプレート（ヘッダーと奥付）

文書のメタ情報（題・版・日付・上流依存・著者・配置先）は本文が持たない。**インデックスの `[meta]` が持ち、共有テンプレートが差し込む。** ラベルはテンプレートにだけ書かれるので、文書ごとの表記揺れが構造的に起きない。定型を「守る規約」でなく「破れない構造」にするのがこの据え方の要点である。

```markdown
---
id: meta/header
requires: title, version, date
optional: subtitle, upstream, status
raw: true
---
# {{meta:title}}
## {{meta:subtitle}}

**Upstream:** {{meta:upstream}}

**Version:** {{meta:version}}
**Date:** {{meta:date}}
```

- **行落ちの規則：** ①`optional` に挙げたメタが `[meta]` に無いとき、そのトークンを含む行を落とす。②トークンを埋めた結果、空白だけになった行を落とす。この二つが唯一の条件分岐であり、テンプレート言語は作らない。`optional` に挙げていないキーが `[meta]` に無ければ、行落ちでなくエラーになる（黙って消えない）。文書の種類ごとの差（README の `Status`、原典の上流依存、補足に著者が無いこと）は、この規則で吸収する。テンプレートを種類別に増やさない。
- 行落ちが空行の重複を生まないよう、任意の行はテンプレート上で前後に空行を置かない書き方に限る。
- 奥付（`meta/colophon`）も同じ値を差し込む。同じ値が二か所に字面で並ぶ状態を作らない。
- **テンプレートは種別ごとに一つ。** 骨格は文書種別の属性なので、種別の違う文書を一つのテンプレートへ押し込まない。現在あるのは原典向け（`meta/header` / `meta/colophon` / `license/cc-by-4.0`）と補足向け（`meta/supplement-header` / `meta/supplement-colophon` / `license/supplement-cc-by-4.0`）。補足は、上流依存の欄の代わりに関連（原典と姉妹補足）を持ち、ライセンスの配置先 URL を改行して置く——**字面が違うので、行落ちの規則では吸収できない。** 一件しかない文書（README の `Status`・`Friction & Proof`）は、種別を立てずに文書側のモジュールへ置き、値は同じ `[meta]` から差し込む。
- ラベル・版の書式・括弧書きを置かない規約は CONTRIBUTING が持ち、その機械的な担保は lint が持つ（§13）。

## 8. インデックス

文書ごとに 1 つ、TOML で書く。**単一言語の文書も日英の文書も同じ形**（ブロックが 1 つか複数かの違いだけ）。

```toml
[doc]
id      = "shisaku-human-idion-structure"
output  = "{{path:shisaku-human-idion-structure}}ja/shisaku-human-idion-structure.md"

[meta]
title     = "シサク・ヒト IDION 構造理論"
subtitle  = "Shisaku Human IDION-Structure Theory"
version   = "v0.1.6"
date      = "2026/09/12"
author    = "shisaku"
upstream  = "シサク・ヒト変容理論（SHTT）→ 前提優位理論（Premise Primacy）／最上流：シサク・世界解釈"
canonical = "{{url:shisaku-human-idion-structure}}"
license_intro  = "This document (Shisaku Human IDION-Structure Theory) is …"
copyright_year = "2026"

[numbering]
enabled = true
start   = 0                      # 最初の番号付き見出しの番号
format  = ["{n}. ", "{n} "]      # 深さごとの番号の書式（深さ 1、深さ 2 …）
sub_start = 1                    # 深さ 2 以下の最初の番号

[[block]]
lang          = "ja"
base_depth    = 1
cluster_depth = 1                    # 先頭 1 セグメントは所属（役）＝深さに数えない
render        = { sec = "第{n}節" }  # このブロックでの {{sec:…}} の描画
groups = [
  ["shared:meta/header", "document/epigraph"],
  ["document/preface"],
  ["subject/definition"],
  ["subject/strength", "subject/strength/combination-rule", "subject/strength/contour-definition"],
  ["subject/discriminators", "document/six-requirements"],
  ["shared:meta/colophon"],
  ["shared:license/cc-by-4.0"],
]
```

日英を持つ文書は、ブロックを並べる。

```toml
[doc]
id     = "readme"
output = "README.md"

[[block]]
lang       = "common"
base_depth = 0
groups     = [["header"]]

[[block]]
lang       = "ja"
base_depth = 1
render     = { sec = "第{n}節" }
groups     = [["what-is", "what-is/name"], ["repository"], …]

[[block]]
lang           = "en"
base_depth     = 1
render         = { sec = "Section {n}" }
groups         = [[], ["banner"], ["what-is", "what-is/name"], …]
allow_unpaired = ["banner"]      # 対になる相手を持たないことを許すモジュール

[[block]]
lang       = "common"
base_depth = 1
groups     = [["colophon"]]
```

- **文書のメタはインデックスが持つ（`[meta]`）。** モジュールの本文には書かない。ヘッダーと奥付は共有テンプレート（§7.5）が差し込む。版の書式と、版が `v0.x.y` を出ない規約は CONTRIBUTING が持つ。
- `lang` はモジュールを探すディレクトリ名（`ja` / `en` / `common`）。
- `base_depth` ＝ そのブロックの最上位見出しの深さ。`base_depth = 1` なら、id が 1 階層のモジュールの先頭 H1 は `##` になる。
- 深さ ＝ `base_depth` ＋（id の階層数 − `cluster_depth` − 1）。`cluster_depth` の既定は 0（所属を持たない文書）。モジュールの `level` はこれを上書きする（例：英語ブロックの `banner` は `level = 1` で `#` のまま）。
- **共有モジュール（`shared:`）の id はリポジトリ内の置き場であって文書の階層ではない。** 深さも採番も 1 階層として扱い、変えたいときは `level` で指定する。
- **区切り線はインデックスが持つ。** モジュールの中に置かない。実物の区切り線は一様ではない（弁別子と六要件の間には無い、日英の境目は二重）。区切り線は「まとまり」という構造情報なので、並びを持つ側の管轄になる。モジュールに持たせると、並べ替えたときに線だけが取り残される。
- **空のグループ（`[]`）は区切り線だけを出す**（前後に空行を足さない）。日英の境目の二重線はこれで表す。

## 9. 連結規約（バイト一致の条件）

出力は次の規則で組み立てる。実測した既存文書の形に合わせてある。

- モジュールの本文は、前後の空白を落として（末尾の改行を含む）扱う。
- **同じグループ内**のモジュールは `\n\n`（空行 1 つ）で連結する。
- **グループ同士**は `\n\n---\n\n` で連結する。
- **ブロック同士**もグループの連結と同じに扱う（ブロックの境目に特別な規則を置かない。日英の境目の二重線は、空グループで表す）。
- 出力は改行で終える（最終行を改行で終端する。空行を足すのではない）。現在 README は改行で終わっていないので、構造を揃える工程で終端しておく。

## 10. トークン

本文中の置換はすべて `{{種類:キー}}` の一つの形に揃える。解決器・エスケープ・未解決の検出が一つで済む。

| 種類 | 例 | 解決結果 |
| :-- | :-- | :-- |
| `sec` | `{{sec:strength}}` | `第4節 強度`（そのブロックの `render.sec` の書式。`{n}`＝番号・`{t}`＝題） |
| `num` | `{{num:strength/combination-rule}}` | `4.1` |
| `title` | `{{title:disguise}}` | そのモジュールの題（番号を含まない） |
| `path` | `{{path:shisaku-human-idion-structure}}` | `concepts/human/shisaku-human-idion-structure/`（リポジトリのルート基準） |
| `url` | `{{url:shisaku-human-idion-structure}}` | `https://…/tree/main/concepts/human/shisaku-human-idion-structure` |
| `meta` | `{{meta:version}}` | インデックスの `[meta]` の値 |

- **`render.sec` に `{t}`（題）を置けるのは、節名が参照の宛先だからである**（`authoring-policy.md`「相互リンク規約」の節）。番号だけでは、跳ばないと何の節か分からない。番号を先に置くのは、**出力の 7 割が著者の括弧の中にあり**、題を括弧付きで出すと入れ子になるためである。
- リテラルの `{{` を書きたいときは `\{{` と書く（出力は `{{`）。対象文書での `{{` の出現は 0 件。
- 解決はコードフェンス・コードスパンの内側でも行う。README のパス言及はバッククォートの中にあるため。
- 解決の順序：モジュール読み取り → 構造の確定（深さ・番号） → トークン解決 → 連結。番号が確定してからでないと `sec` / `num` が解けない。
- 未解決のトークン（存在しない id・キー・未知の種類）は、一覧を出して終了コード 1 で止める。解決できないまま出力しない。
- `[meta]` の値に含まれるトークンは再帰的に解決する（深さの上限 5・循環はエラー）。
- 文書をまたぐ参照は `{{sec:<文書id>/<モジュールid>}}` の形を**予約だけ**する。第一陣では実装しない。他文書への参照は字面のまま残す。

## 12. 採番

- 番号は `[numbering] format` の書式で、その深さの連番として合成し、先頭見出しの題の前に置く。
- 採番の深さ ＝ id の階層数 − `cluster_depth`（所属は数えない）。
- 連番は**ブロックごと・深さごと**に数える。`numbered = false` のモジュールは数えない（連番から外れる）。深さ 2 の連番は、親（深さ 1）が変わるたびにリセットする。
- 深さ 2 以下の番号は、親の番号を継いだ形（`4.1`）で描画する。
- IDION の実物に合わせる形は `format = ["{n}. ", "{n} "]`、`start = 0`（`## 0. …` / `### 7.1 …`）。
- 本文に手書きの番号が残っている場合、モジュール化の途中では字面のまま置き、採番へ切り替える工程で取り除く。

## 14. インターフェース（CLI）

監査の材料を出す口（`--audit`・`--refs`）は、判定を持たない——出すのは材料だけで、裁定は人が行う（`AUDIT.md` §3）。


```bash
python3 src/engine/build.py                                # 全文書をビルド
python3 src/engine/build.py shisaku-human-idion-structure  # 文書を指定（[doc] id ＝ディレクトリ名）
python3 src/engine/build.py --check                        # 組み立て結果と出力先の一致を検査（書き出さない）
python3 src/engine/build.py --lint-only                    # 静的検査のみ
python3 src/engine/build.py --audit                        # 監査の材料を出す（判定はしない）
python3 src/engine/build.py <doc> --refs <id>              # そのモジュールの影響半径
python3 src/engine/build.py --audit-file <path>            # まだ載せていない文書に材料を出す
python3 src/engine/build.py --impact                       # 変更したモジュールの影響半径（必須調査）
```

- 文書の指定は完全一致だけを受ける。省略形・部分一致は持たない（常用は引数なしのビルドであり、名を打つ機会は稀）。

- 既定はビルド（出力先へ書き出す）。
- `--check` は、組み立て結果を**出力先の現在のファイル**と比べ、違えば差分の要約を出して終了コード 1 で止める。
- lint のエラーは、ビルド・`--check` のいずれでも、書き出しの前に止める。

### 14.1 用語の関門（`terms.py`）

**目印の走査範囲。** `concepts/`・`src/docs/`（生成物を除く）に加えて、**リポジトリ直下の資料作成オペレーションルール**（未モジュール化だが、台帳のバンドルの正本を持つ）。直下の他の文書は目印を持たない。検出 (c) が見出しを集める直下の文書にも、同じ規約を加えてある。

**別の入口を立てている。** 文書ビルドは `src/docs/` のインデックスを持つ文書だけを扱うが、用語の関門は**インデックスを持たない文書も見る**（補足 4 本は、まだモジュール化していない）。射程が違うので、`build.py` の一機能にしない。

`python3 src/engine/terms.py` —— 台帳（`terminology-ledger.md`・正本）と本文の目印を突き合わせる。**エラーが 1 件でもあれば終了コード 1。**

| 記号 | 何を見るか | 効き |
| :-- | :-- | :-- |
| C1 | 台帳の正本の位置が、目印のある節と一致するか | 確実 |
| C2 | 本文の目印の名が台帳にあるか | 確実 |
| C2' | 台帳の行に、本文の目印があるか | 確実 |
| C3 | 台帳の要素が、その節の本文に逐語で在るか | **片側だけ**（本文に余分があっても出ない） |
| C4 | 一語一軸（用語規約 第1条） | 確実。ただし**台帳に載っている語だけ** |
| C5 | バンドル名が、裸の登録語と同じでないか | 確実 |
| C6 | 開閉の宣言があるか | 確実 |
| C7 | 一つの裸形が二つ以上のバンドルを指していないか | 確実（警告） |
| C8 | 仕組みの語が原典の語と重なっていないか（第12条） | **台帳に載っている語だけ** |

**判定できないものは、数えて出す。** 範囲表記（`予測1〜6`）の要素は本文と逐語照合できない。正本の位置に節名が書かれていない行も照合できない。`AUDIT.md` の分界（機械が判定するもの／材料だけ出すもの／人が決めるもの）に従う。

**生成物は走査しない。** インデックスの `output`（`{{path:…}}` を `paths.toml` で解いたもの）を除く。除かないと、モジュールと生成物で目印が二重に数えられる。

**この関門が塞がない穴。** 「台帳に無い名が本文で使われた」は、名が日本語の句なので全件は拾えない（用語規約 第11条が同じことを書いている）。C4・C8 は**台帳の網羅性に依存する**——載っていない語は当たらない。

### 14.2 検出（`terms.py --detect`）

**関門でなく材料である。判定しない。終了コードは常に 0。** 射程が現ブランチの 6 文書を超え（`concepts/` の公開文書 33 本）、**この枝では直せない文書の件が大半を占める**ため、止める関門にすると誰も回さなくなる。`AUDIT.md` の分界（機械が判定するもの／材料だけ出すもの／人が決めるもの）の二番目に置く。

| | 何を出すか | 精度を決めるもの |
| :-- | :-- | :-- |
| (a) | 番号で範囲を指す参照（`第1〜7節`・`①〜④`・`1〜10`） | **台帳の `ordinal` の網羅性。** 番号が身元である列（予測・事例・前提…）を除外するので、**台帳に載っていない列は誤検出として残る** |
| (b) | 補足からの節番号参照（`authoring-policy.md` の相互リンク規約が禁じる） | 補足の判別。**文書自身の宣言（H1 に「補足」）で当てる**——ファイル名で当てると `…-canon.md` を取り違える |
| (c) | 「…」の節 で参照された名が、どの見出しにも無い件 | 見出しの収集範囲（`concepts/` とリポジトリ直下の規約類） |
| (d) | 同じ名の直後の列挙が、文書間で違う件 | 台帳の別名。**三文字未満の裸形は検索鍵にしない**（「層」「出口」「候補」は第5条 (i) の節内呼称としては正しいが、文書をまたぐ鍵にならない）。**二つ以上のバンドルを指す裸形も鍵にしない**（C7 が別に出す） |

**(a) の誤検出は、台帳の被覆率の指標である。** 現在 6／23 文書しか登録していないので、残り 17 文書の番号列（`①〜④`・`原理1〜4` など）は正常な用法なのに出る。**件数が減ることが、登録が進んだことの証拠になる。**

## 15. 実行環境

- Python 3.11 以上（`tomllib` を使うため）。macOS 標準の `/usr/bin/python3` は 3.9 で、これには含まれない。3.11 未満のときは `tomli` があればそれを使い、どちらも無ければ理由を示して止める。
- 標準ライブラリのみ。外部パッケージに依存しない。
- `build.py` の冒頭で `sys.dont_write_bytecode = True` を設定し、バイトコードのキャッシュ（`__pycache__`）を作らせない。無視設定に頼らず、clone 先でも同じように振る舞わせるため。
- **この保証は `build.py` を経由したときだけ効く。** `docbuild` を直接 import する経路（対話実行・テスト）ではキャッシュが作られる。作られた `__pycache__` はコミットしない。

## 16. 文書ごとのモジュール構成

### 16.1 README

言語を持たないモジュール（`common/`）：`header`（題と版のブロック）、`colophon`（末尾のメタ）。値は `[meta]` から差し込むが、README 固有の項目を持つためテンプレートは共有しない。

日英で対になるモジュール（id は共通）：

`repository` / `what-is` / `what-is/name` / `what-is/failure-analysis` / `what-is/origin` / `readers` / `how-to-read` / `concepts` / `concepts/shisaku-world-interpretation` / `concepts/shisaku-social-renewal-interpretation` / `concepts/premise-primacy` / `concepts/shisaku-prediction-model-interpretation` / `concepts/shisaku-qualia-interpretation` / `concepts/shisaku-value-interpretation` / `concepts/shisaku-cognitive-frame` / `concepts/shisaku-human-transformation` / `concepts/shisaku-human-idion-structure` / `concepts/kosei-mining` / `not-included` / `participation`

英語のみ：`banner`（`# shisaku-method (English)`・`level = 1`）。`allow_unpaired` に登録する。

- 概念を指すモジュールの名は、その概念のディレクトリ名と同じにする（`paths.toml` のキーとも一致する）。短縮名を作らない。
- 概念の項目を 1 モジュールにするのは、概念の追加がこの文書で最も頻繁に起きる更新であり、追加がファイル 1 つとインデックス 1 行で済むようにするため。
- **README は索引であって網羅ではない。** 載せるのは主要な概念だけで、`concepts/` の全件ではない。並びは**上流から下流へ**——各文書が自分で書いている上流依存で決まる。全件を載せると、概念が増えるたびに入口が長くなり、どれから読むかが読めなくなる。
- `concepts` は見出しだけを持つモジュール（本文は無い）。
- README は現在ライセンス表示を持たない。持たせるかどうかは本書の管轄外。

### 16.2 IDION 原典

所属（役）でディレクトリを切る。ディレクトリが表すのは**役であって位置ではない**——「序」は位置が先頭なだけで、役は文書についての節である。

```
ja/
├── subject/                        # 対象について
│   ├── definition.md               0  定義と把手
│   ├── axiom.md                    1  公理
│   ├── extension.md                2  外延
│   ├── structure.md                3  構造
│   ├── strength.md                 4  強度
│   ├── strength/
│   │   ├── combination-rule.md     4.1
│   │   └── contour-definition.md   4.2
│   ├── judgment-asymmetry.md       5  判定の非対称
│   ├── disguise.md                 6  偽装
│   ├── dignity.md                  7  品格
│   └── discriminators.md           弁別子（各節の集約＝派生・将来は生成）
│
├── application/                    # 適用について
│   ├── scope.md                    11 適用範囲と境界  ＝用法条件
│   └── ethics.md                   12 倫理条項        ＝用法条件
│
└── document/                       # 文書について（身分）
    ├── epigraph.md                 題辞       ＝読み方の宣言
    ├── preface.md                  序         ＝目的
    ├── novelty.md                  13 新規性  ＝意味（兄弟との差別化境界）
    ├── grounding.md                9  接地    ＝根拠
    ├── falsification.md            10 反証条件 ＝効果と失敗機構
    ├── upstream.md                 8  上流接続 ＝系の中での位置
    ├── six-requirements.md         本書の六要件 ＝目的・目標の枡
    ├── naming.md                   命名   （maturity: pending）
    └── open-items.md               未決   （maturity: pending）
```

- 「命名」「未決」は裁定待ちだが、それは**成熟度であって役ではない**。所属は `document/`（この文書についての宣言）に置き、状態は `maturity: pending` で持つ（§3.5）。
- **`application/` には、測定（観測手続き）と誤用の型の枡が空いている。** BOK との同型で出た欠け（§3.2）であり、他の文書には実在する節（警告・対象者）が、本書には無い。枠が空いていることが見える状態を保つ。
- `document/` の並びは出力順ではなく**六要件の枡の順**である。埋まっていない枡（目的と目標を 1 本が兼ねていること）が、ディレクトリの中身として見える（§1.3）。
- ヘッダー・奥付・ライセンスは共有モジュール（`shared:`）なので、この木には現れない。
- 下位節（4.1・4.2）を割る根拠は、本文から独立に参照され、独立に改訂されている実測（§3.1）。
- 「弁別子」は各節の規則の集約で、節を直せば一緒に動く＝独立の裁定単位ではない。第一陣では 1 モジュールとして置き、生成へ移すのは後（§17）。
- `header` と `colophon` は、題・上流依存・版・日付を重複して持つ。値は `[meta]` に置き、共有テンプレート `shared:meta/header` / `shared:meta/colophon`（§7.5）で差し込む。版上げがインデックスの 1 か所で済む。
- ライセンスは共有モジュール（§7.4）を呼ぶ。ただし字面のまま移す工程では文書ごとのモジュールで置き、共有部品への切り替えはその後の正規化として行う。

### 16.3 IDION 補足 4 本

原典と同じく所属（役）でディレクトリを切る。**補足は原典に無い役を一つ持つ**——`canon/`（原典について・§3.2）。

```
idion-supplements/
├── idion-axes-map/          document/placement・failure-modes ／ subject/axes・objects・independence・receiver-mapping ／ canon/feedback
├── idion-cost-forms/        document/placement・failure-modes ／ subject/forms・variables ／ application/distinctions・screening ／ canon/feedback
├── idion-system-isomorphism/ document/placement・failure-modes ／ application/correspondence・change-kinds・procedure ／ subject/where-it-breaks ／ canon/feedback
└── idion-cases/             document/placement ／ application/procedure・split-detection ／ canon/cases・feedback・observations
```

- **27 節のうち `canon/` は 6 節**——4 本それぞれの「原典へのフィードバック候補」、`idion-cases` の「事例集」と「分離候補の観察欄」。
- **`canon/` の一問には、一段の区別が要る。** 条文は「その節が語っているのは、この文書の外にある原典か」だが、**原典（＝文書）と IDION（＝対象）を分けないと 9 節が鳴る**。`idion-system-isomorphism` の「対応が切れる場所」は IDION（対象）の定義的性質を語るので `subject/`、`idion-cost-forms` の「区別」は原典を**使う**側の規律なので `application/` に入る。§3.2 の条文の手当ては未着手。
- **残り三役の配属に一問は無い**（§3.2 が持つのは枡の定義だけ）。ここでの 21 件は判別子なしの配属であり、**前例になる**。理由は維持側の記録に残してある。
- **二役にまたがる節が 2 件ある**——`idion-cases` の「分離検出」（検出の手続き＋原典が語を分けた実績）と `idion-axes-map` の「軸の独立性」（二基準＋6 対の評価）。**本文を動かさないため寄せて置き、混在の注記はインデックスに置いた**（本文に書けば字面が動く）。割る是非は、原因（上流に正本が無いこと）の手当てと一緒に決める。
- **`idion-cases` には「失敗機構」の節が無い。** 他の 3 本にはある。欠落が補足側か、様式を定める規約側かは決まっていない。
- 補足の骨格（位置づけ／篩の手続き／非固定の明記／原典へのフィードバック欄）は `authoring-policy.md` が条文として持つ。**4 本はそれに従っている。**
- **`idion-axes-map` は、見出し欄の版（v0.1）と奥付の版（v0.1.1）が食い違っている。** 字面を変えないため、インデックスは `header_version` と `version` を別に持つ。**二つの版を持つこと自体が直す対象**であり、一致させる改訂は裁定を経てから行う。
- ヘッダー・奥付・ライセンスは補足向けの共有テンプレート（§7.5）を呼ぶ。

### 16.4 シサク・予測モデル解釈

**役でディレクトリを切らない。平置きにする。** 四役（`subject/` / `application/` / `document/` / `canon/`）の導出は**六要件の再帰適用**と **BOK との同型**の二経路から来ている（§3.2）。解釈は六要件を持たない種別（`authoring-policy.md`「種別」の節）なので、前者の経路が効かない。README と同じく、モジュールの名が節の名を写す平置きにする。

```
ja/
├── preface.md                              0  はじめに
├── general-definition.md                   1  一般にはこう定義されている
├── interpretation.md                       2  私はこう解釈する（見出しのみ）
├── interpretation/
│   ├── expectation-first.md                   予測モデルは、期待を先に出す側である
│   ├── premise-as-state.md                    前提とは、予測モデルが前提として作動している状態である
│   ├── wording.md                             言語化は、実体を移さない
│   ├── example-fj.md                          F と J の突起
│   └── human-side.md                          ヒトの予測モデルは、身体を持つ
├── naming.md                               3  系列の中で、この語をこう名指す
└── substitution-test.md                    4  置換の検査
```

- **第2節の子は `numbered = false`。** 解釈の本論は節の数と粒度が文書に任されており（規約「解釈の必須様式」）、番号は身元にならない。
- **`cluster_depth` を持たない**（既定の 0）。所属を表す先頭セグメントが無いため、深さは id の階層数がそのまま決める。
- 上流依存は `[meta]` の `upstream` が持ち、ヘッダーと奥付に差し込まれる（§16.1 の並びもこの欄で決まる）。解釈は「上流接続」の節を持たない種別だが、上流依存の欄は持つ——載っている解釈は全てこの形（例：シサク・価値解釈「シサク・クオリア解釈 → シサク・予測モデル解釈」・シサク・社会更新解釈「シサク・世界解釈」）。
- ヘッダー・奥付・ライセンスは共有モジュール（§7.5）を呼ぶ。

## 17. 予約と未決

- **横断の検査。** 骨格の埋まっていない枡（種別ごとの様式に依存）／用語の軸の衝突／二重定義。
- 文書をまたぐ参照（`{{sec:<文書id>/<id>}}`）。他の原典が載ってから。
- 出力位置基準の相対パス（`{{rel:…}}`）。同一ディレクトリ内の参照しか無い間は要らない。
- 「弁別子」を各節から生成すること。
- 全文書の `[meta]` を一覧に出す（`build.py --meta`）。どの文書が今どの版か、更新日はいつかを、ファイルを開かずに引けるようにする。メタの置き場が決まっていれば後から足せる。
