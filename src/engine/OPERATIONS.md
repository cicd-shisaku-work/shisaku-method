# シサク原典管理スクリプト運用手順書

**Version:** v0.1.3
**Date:** 2026/09/15
**性格：** `src/` の文書ビルドを日々どう回すかの手順。仕組みそのものの設計は `DESIGN.md`。本書は「何をどの順で叩くか」「コミットに何を入れるか」だけを扱う。

---

## 1. 基本の規律

- **生成物を直接編集しない。** `README.md` や原典の本文をエディタで直したくなったら、対応するモジュールを直す。
- **ソースと生成物を同じコミットに入れる。** 片方だけのコミットは、正本と生成物が食い違った状態を履歴に残す。
- **直すモジュールを参照している側と突き合わせる（`--impact`・必須）。** モジュールは編集の単位であって読む単位ではない。局所で正しく全体で矛盾する、を防ぐのは人の突き合わせであり、機械は材料を揃えるだけである（設計書 §2）。
- **ビルドしてからコミットする。** 生成物であることを示すヘッダ行は文書に入れていないため、直接編集のずれを見つける手段は `--check` だけになる。

---

## 2. 文書を直す

```bash
# 0. 影響半径を出す（必須）。直す前でも、直した後でもよいが、コミット前には必ず通す
python3 src/engine/build.py --impact

# 1. モジュールを編集する
#    src/docs/root/readme/ja/… や src/docs/concepts/<文書>/ja/… など

# 2. ビルドする
python3 src/engine/build.py

# 3. 差分を見る
git diff

# 4. 影響半径を出し直し、参照している側と突き合わせる（必須）
python3 src/engine/build.py --impact

# 5. ソースと生成物をまとめてコミットする
git add src/ README.md
```

**影響半径の突き合わせは必須の調査である。** モジュールは編集の単位であって読む単位ではないので、局所で正しく全体で矛盾する、を防ぐのはこの突き合わせしかない（`AUDIT.md` §1.5）。とくに **`※ 役をまたぐ波及`** と出た参照は、役が違う＝文脈が違うところから指されているので、当たり方がずれやすい。

突き合わせた結果は、**PR 説明に 1 行残す**（どのモジュールの影響半径を見て、どこを直した／直す必要がなかったか）。残さなければ、やったかどうかを誰も確かめられない。

版を上げるときは、インデックス（`src/docs/<区分>/<文書>/index.toml`）の `[meta] version` と `[meta] date` を直す。本文には版を書かない（冒頭のヘッダーと末尾の奥付の両方へ、トークンで差し込まれる）。版が `v0.x.y` を出ない規約と、ヘッダーの定型は CONTRIBUTING §4。

---

## 3. モジュールを足す

1. モジュールのファイルを置く（`src/<文書>/<言語>/<id>.md` または `.xml`）。
2. インデックスの `groups` の、入れたい位置に id を書く。
3. 日英を持つ文書なら、対になるモジュールを両方の言語に置く（置かないなら `allow_unpaired` に登録する）。
4. `python3 src/engine/build.py` を実行し、意図した位置・深さ・番号で出ているか見る。

---

## 4. 文書を新しく載せる

1. `src/docs/<区分>/<文書>/index.toml` を作る（`DESIGN.md` §8 のスキーマ）。`[meta]` に版・日付・ライセンスの一文・配置先 URL を置く。
2. 既存の文書を、内容を変えずにモジュールへ割る。
3. `python3 src/engine/build.py <文書id> --check` が通る（＝バイト一致する）ことを確認する。**ここが関門。** 一致してから、はじめて内容の編集に入る。
4. 手書きの番号・パス・参照をトークンへ置き換える。置き換えるたびに `--check` を通し、出力が変わっていないことを確かめる。

---

## 5. 配置換え（`concepts/` を動かすとき）

1. `git mv` で実体を動かす。
2. `src/paths.toml` の該当行を新しいパスに直す。
3. `python3 src/engine/build.py` を実行する。インデックスの出力先・本文中のパス言及・canonical URL が、まとめて新しいパスへ解決される。
4. `python3 src/engine/build.py --lint-only` で、対応表のパスがすべて実在することを確認する。
5. **トークンで表せない 2 か所は手で直す。** README の構造ツリーの木と、`-trajectory-structure/` のような略記。

---

## 6. 検査

```bash
python3 src/engine/build.py --lint-only   # 静的検査だけ
python3 src/engine/build.py --check       # 生成物が最新かを検査（書き出さない）
python3 src/engine/terms.py               # 用語の関門（台帳と本文の目印を突き合わせる）
python3 src/engine/terms.py --detect      # 検出（材料を出す・止めない）
```

- `--check` が落ちたときは、生成物が直接編集されたか、モジュールを直してビルドし忘れたかのどちらか。差分を見て、直接編集だったならその変更をモジュール側へ移し、ビルドし直す。
- lint のエラーはビルドを止める。よくある原因は、インデックスに書いた id のつづり違い、対応表に無いキー、対になるモジュールの置き忘れ。
- **`terms.py` を回すのは、語かバンドルを立てたとき・本文の列挙を直したとき・PR の前。** 仕様は `DESIGN.md` §14.1。エラーが 1 件でもあれば終了コード 1。
  - **警告と「判定できない」は止めない。** 前者は人が見る材料（裸形が二つのバンドルを指している等）、後者は機械が照合できない形（範囲表記の要素）。`AUDIT.md` の分界と同じ。
- **`--detect` は関門でない。** 材料を出すだけで、終了コードは常に 0（`DESIGN.md` §14.2）。射程が現ブランチを超えるので、**直せる文書の件だけを拾って使う**。
  - **落ちたときの直し方は二通り。** 台帳が本文とずれている（台帳を直す）か、**本文に穴がある**（原典を直す）か。**行が書けないなら埋めない**——用語規約 第11条。

## 7. 監査を回す

監査の目的・対象・分界は `AUDIT.md`。ここは回し方だけを書く。**監査は本文を直さない**——材料を出し、裁定の要る項目を並べるところまでが仕事である。

### 7.1 材料を出す

```bash
python3 src/engine/build.py --audit                      # 全文書の材料（ビルドに載っている文書）
python3 src/engine/build.py --audit-file <path>          # 収録前の文書（まだモジュールでない）
python3 src/engine/build.py <文書id> --audit             # 文書を指定
python3 src/engine/build.py --impact                      # 変更したモジュールの影響半径（必須調査）
python3 src/engine/build.py <文書id> --refs <モジュールid>  # 1 本を指定して影響半径
python3 src/engine/build.py --lint-only                  # 機械が判定する面
python3 src/engine/build.py --check                      # 生成物が最新か
```

`--audit` が出すもの。

| 材料 | 読み方 |
| :-- | :-- |
| 粒度の分布 | **散らばり（最大÷中央）で見る。絶対値では見ない**——種別で桁が違う（ランタイム文書の中央 120 字、原典 957 字） |
| 採番（収録前のみ） | 番号あり・なしの同居、番号の深さの混在。参照の形式が定まらない兆候 |
| 他文書への参照（収録前のみ） | 位置依存ではないが、配置換えで壊れる。対応表に載っていない宛先がないか |
| 位置依存の参照 | 「前述」「上記」「次節」——名前参照へ変換できない書き方。並べ替えで静かに壊れる |
| 被参照の多い順 | 多いものは土台。触るときの影響が大きい |
| 相互に参照し合う対 | **割ってはいけないものを割った疑い**。回数が多いほど強い信号 |
| 参照も被参照も無いモジュール | 孤立。定型（ヘッダー・奥付・ライセンス）は正常。それ以外は、載せる必要があるかを問う |

### 7.2 いつ回すか

| 契機 | 回すもの |
| :-- | :-- |
| 文書を新しく載せる前 | `--audit-file` → 構造点検（`AUDIT.md` §5）→ 整えてから割る |
| モジュールを直すとき | `--impact`（変更されたモジュールをまとめて）／`--refs`（1 本を指定） → 参照している側と突き合わせる。**必須** |
| ビルド・インデックスを変えたとき | `--check`・`--lint-only` |
| コミット前 | `--check`・`--lint-only` |

### 7.3 差し戻しの様式

材料をそのまま貼らない。裁定できる形にして差し出す。1 項目につき、次の 4 つを 1 行ずつ。

1. **観測**：何が出たか（数値・件数・箇所）
2. **解釈**：それが何を意味しうるか（断定しない）
3. **裁定が要る点**：何を決めてほしいか（一問）
4. **決めた場合に動くもの**：どのファイル・どの参照が動くか

材料の量が多いときは、**信号の強い順に並べ、弱いものは件数だけを述べる**。全件を並べると、裁定する側が読む仕事を肩代わりすることになる。

## 8. ライセンスを差し替える

1. `src/shared/license/<ライセンス名>.md` を作る（文書ごとに変わる部分は `{{var:…}}` で空ける）。
2. その文書のインデックスで、`shared:license/cc-by-4.0` を新しい id に差し替える。
3. `[meta]` に、新しいモジュールが要求する値を足す。
4. ビルドして差分を見る。

ライセンスは文書ごとの選択であり、共有モジュールは既定を用意するだけ（CONTRIBUTING §4）。

---

## 9. コミットの作法（CONTRIBUTING に従う）

- 型は、モジュールを直して内容が変わるなら `docs:`、仕組み側だけなら `chore:`。
- 要約と本文は英語。本文には、文書ごとの箇条書きと改訂の根拠を書く。
- 本リポジトリの外の名前・パス・節番号に依存しない。根拠は役割で書く。
- 生成物とソースが同じコミットに入っていることを、`git status` で確認してから commit する。

---

## 10. 規約との関係

本書は手順であって規約ではない。PR が満たすべき条件（生成物を直接編集しない／`--check` が通る／影響半径を突き合わせる）は **CONTRIBUTING §3 のチェックリストが正本**であり、ここには写さない。同じ事実を二か所に置くと、片方だけが更新されて食い違う。
