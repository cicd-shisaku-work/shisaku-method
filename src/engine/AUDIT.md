# 監査の思想と設計

**Version:** v0.1.4
**Date:** 2026/09/25
**性格：** ビルドに載る文書に対する監査の、目的・対象・分界・失敗機構を定める。実行の手順は `OPERATIONS.md`「監査の実行」、機械の検査仕様は `DESIGN.md`（lint・`--check`・`--refs`）が持つ。本書はそれらを参照し、二重に書かない。

---

## 0. 射程

**対象：** `src/docs/` にモジュールを持つ文書と、これから載せる文書。

**判別子は一問——その文書は、ビルドに載せると決まっているか。** 決まっていれば（収録の申請があれば）対象になり、収録前の構造点検が掛かる。「いずれ載るかもしれない」は対象でない。決めていない文書まで対象にすると、`concepts/` 全体が暗黙の対象になり、射程が数えられなくなる。

**対象外：** `logs/`（証跡）、`publications/tmp/`（仮置き）、載せると決めていない文書、モジュール化しない文書。

対象は数えられる（`src/docs/` の中身と、収録の申請）。「すべての文書」のような、数えられない対象を持たない——数えられない対象を宣言した規約は、広すぎて形骸化するか、当たらない文書にまで当てて硬直する。

**昇格の条件：** ビルド外の文書にも同じ監査を掛ける必要が出たときは、本書をリポジトリ直下へ移し、射程を書き換える。そのときまで、ここに置く。

---

## 1. なぜ監査が要るか

### 1.1 実装の側の出力は、照合を経ていない

設計も実装も、実装の側が書く。書けるのは「もっともらしく整った構造」までで、それが所有者の判断を担持しているかは、**所有者が照合するまで決まらない**。照合を経ていない構造が所有者の名義で流通すれば、それは偽装になる。**監査は品質管理ではなく、成果が誰のものかを決める手続き**である。

### 1.2 機構の正しさと、設計の正しさは別の軸

バイト一致のゲート（`--check`）が証明するのは、組み立てが元の文書を壊していないことだけである。**割った線が裁定の単位か、ディレクトリがロールに対応しているか、名が正しいかについては、一言も言っていない。** 機械の門番は前者しか見張れない。ここを取り違えて「検査が通った＝設計が正しい」と読むのが、最も起きやすい失敗である。

### 1.3 土台裁定は、下流の形を決める

ディレクトリ・id・参照の形は、これから載る文書すべての形を決める。据わりが誤っていれば、気づいた時点で全文書の書き換えになる。**実装が動いていることは、据わりの証明にならない。**

### 1.4 導出は、内部整合しか保証しない

「目的から導出した」と言っても、**目的の立て方そのものが誤っていれば、整合した誤りができあがる**。導出は前提から結論への道を保証するだけで、前提の正しさは保証しない。前提を外から突く手続きが、導出とは別に要る。

### 1.5 部分最適化は、局所の検査では原理的に見えない

各モジュールが局所で正しく、全体で矛盾する（`DESIGN.md` §2）。モジュール単位の検査をいくら厚くしても検出できない。**全体を見る目が、独立して要る。**

### 1.6 規約と実装は、時間でずれる

一度きりでは足りない。設計書を書いた直後の自己監査だけで、設計と実装の食い違いが 8 件出た（`level` の意味、共有モジュールの深さ、空グループの連結、孤児検査、など）。**書いた時点で合っていても、触るたびにずれる。**

### 1.7 不整合を最初に踏むのは、読者でなく編集の側である

本リポジトリの原典を端から端まで通読する人は、多く見積もっても数人から数十人のオーダーである（入口の読者 10^2〜10^3／年から、外部リポジトリへの到達率 1〜3%、密な非入口の文書の通読率を掛けた見積もり。錨にした出所は二つ——note の会員数と投稿数〔note 社の公表・2025 年〕、Kindle 個人出版の平均販売部数〔出版支援側の経験則・調査データではない〕——で、他の段は推定である。**人数の断定には使わない。桁の見当まで**）。いま通読しているのは、人より、上流と下流を突き合わせる編集の側——改訂のたびに原典を読み直すセッション——である。

ゆえに不整合の費用は、読者より先に編集の過程に落ちる。上流を直したのに下流が古いまま残る、同じ語が二つの文書で違う定義で並ぶ——それを最初に踏むのは次の改訂であり、踏んだところで再導出が起きる。監査が要る理由の一つは、この費用を編集の過程の中で先に見つけることにある。**読者が少ないことは、整合を後回しにする理由ではなく、監査が読者でなく編集の側を守るものだという事実の言い換えである**（整合をいつ取るかは `authoring-policy.md`「上流優先の編集」の節が持つ）。

## 2. 何を監査するか（四つの対象）

| # | 対象 | 見るもの |
| :-- | :-- | :-- |
| 1 | **文書の構造** | ロールの単一性、枠の欠落と余り、位置依存の参照、二重記述、粒度の分布 |
| 2 | **モジュールと参照** | 分割線（割ってはいけない対を割っていないか）、影響半径、孤立モジュール、**文書をまたぐ参照**（配置換えで壊れる） |
| 3 | **生成物** | 出力が最新か、出力の変化が意図した分だけか |
| 4 | **設計書と実装の一致** | 設計書に書いた規則が、実装とツリーに実在するか |

**骨格の判定単位は、必ずしも文書ではない。** 文書の中に「生成される文書の型」が入ることがある（テンプレートを持つランタイム文書など）。そのとき H2 は文書の骨格でなく型の骨格を表しており、点検票をそのまま当てると誤判定する。**型を含む文書は、型の内側を点検の対象から外す**（型は生成物の様式であって、この文書の骨格ではない）。

**①は、割る前に見るものである。** 整っていない構造をそのまま割れば、乱れが id と参照として固定され、以後ずっと保守コストとして残る。順序は「整える → 割る」であり、逆順にすると参照と id を二度動かすことになる。

## 3. 分界——誰が判定するか

| 面 | 判定 | 例 |
| :-- | :-- | :-- |
| **機械が判定する** | 通る／通らない（ビルドを止める） | id とパスの一致、孤児、未解決トークン、対応表のパスの実在、版と日付の書式、H1 の規律 |
| **機械が材料を揃え、人が判定する** | 材料を見て裁定 | 分割線の密度、影響半径、枠の欠落、粒度の分布、位置依存の参照の一覧、日英の対のずれ、設計書と実装の差 |
| **人しか判定できない** | 裁定 | 据わり（上流整合・非重複・前提構造としての必然）、粒度の是非、名前、目的の立て方そのもの |

**この分界が監査の設計の中心である。** 機械に判定させるのは、判定基準が一意に書けるものだけ。書けないものを機械に持たせると、通ったことを正しさと取り違える（§1.2）。逆に、機械が出せる材料を人に集めさせると、監査は続かない。

**機械の仕事は「検出」ではなく「裁定できる形で差し出す」ことである。**

## 4. いつ回すか

| 契機 | 回す面 |
| :-- | :-- |
| 文書を新しく載せるとき（収録前） | 対象①（構造点検）→ 整えてから割る |
| モジュールを改訂するとき | 対象②（影響半径・`--impact`）→ 参照している側と突き合わせる。**必須**。ロールをまたぐ波及は当たり方がずれやすい |
| ビルド・インデックスを変えたとき | 対象③④（`--check`・設計書との一致） |
| 設計を変えたとき | 対象④（設計書・実装・ツリーの三つ揃い） |
| 版を上げてコミットするとき | 対象③（出力が最新・変化が意図どおり） |

## 5. 構造点検の項目（対象①）

各項目に、判定者と、判定の材料を書く。材料の出し方は `OPERATIONS.md`。

| 項目 | 見るもの | 判定 | 失敗機構（放置するとどうなるか） |
| :-- | :-- | :-- | :-- |
| ロールの単一性 | 一つの節が二つのロール（対象について／適用について／文書について／原典について・`DESIGN.md`「ロール」の節）を跨いでいないか | 人 | 境界が内容とずれ、どちらのロールにも収まらないモジュールが残る |
| 枠の欠落と余り | 六要件の枡のうち埋まっていないもの／どの枡にも載らない節 | 機械が一覧、人が裁定 | 欠落が文章の中に埋もれ、文書ごとに別の骨格が育つ |
| 位置依存の参照 | 「前述」「上記」「次節」など、位置に依存した参照 | 機械が検出 | 並べ替えのたびに静かに壊れる。名前参照へ変換できない |
| 二重記述 | 同じ事実が二か所にある（版・名・定義） | 人（材料は機械） | 割ると二つのモジュールが同じことを言う形で固定され、以後ずっと両方を直す |
| 粒度の分布 | 節の長さの**散らばり**（最大÷中央）。絶対値では見ない——種別で桁が違う（実測：ランタイム文書の中央 120 字、原典 957 字、定義書 879 字） | 機械が計測、人が裁定 | 裁定の単位として機能しない（3 行と 3,500 字が同じ「1 モジュール」になる） |
| 採番の一貫性 | 番号つきの節と番号なしの節の同居、番号の深さの混在 | 機械が計測、人が裁定 | 参照の形式が文書ごとに違い、機械で追えない。並べ替えのたびに番号が腐る |
| 文書をまたぐ参照 | 〔ファイル名〕・節名による他文書への参照の数と宛先 | 機械が一覧、人が裁定 | 位置依存ではないが、配置換えで壊れる。対応表に載っていない宛先は追えない |
| 参照の密度 | 相互参照が密な対／どこからも参照されない節 | 機械が計測、人が裁定 | 割ってはいけないものを割った、または載せる必要のない節を載せた |
| 読者の自由の書き方 | 一般読者の面（原典・解釈・補足・フレーム・README）の文を、許可の語（「〜てよい」「〜ていい」）や「〜でよい」で書いていないか。とくに、読者がもとから持つ自由（どの解釈を採るか・自分の身体で判定すること・自分の文書をどう再構成するか）を許可の形で書いていないか——判別子は一問、その自由は、こちらが与えているものか、もとから相手にあるものか。書き手や実装に開けている許容も、一般読者の面では事実の側（できる・成り立つ・済む・足りる）で書く。人の言葉を引いた台詞と、仕組みの文書は対象外 | 機械が構文を一覧、人が裁定 | 「私は裁定者ではない」という文の主張と、文の形が置く関係（許可を与える側）が逆を向く。「よい」は評価の「良い」に読まれ、規則の文が推奨や評価に見える。正の用法は `authoring-policy.md`「本文の文」の節の「許可の語」の小節が持ち、本項は検出だけを持つ |

**「枠の欠落と余り」は、様式が確定していなければ判定できない。** 枠を定めるのは本書ではない。様式は `authoring-policy.md` が持つ——補足の必須様式（五要件）と、**原典の必須様式（六要件・2026/09/17 新設）**。この項目は「どの節がどのロールに属するか」に加えて、**六つの枡が本文のどこで答えられているか**（六要件の節は索引）を材料として出す。埋まっていない枡が欠落、どの枡にも当たらない節が余りである——判定は人が行う。

**種別ごとの点検票——補足。** 補足には、`authoring-policy.md`「補足の必須様式」の節の各項を、そのまま点検項目として当てる（位置づけ〔従属の線・判別子の一問・工学の語で書くならその宣言〕／候補を篩にかける検査手続き／非固定・未証明の明記／原典へのフィードバック候補欄と、版を上げるときの突き合わせ／ライセンス・版）。項目の中身は規約が持ち、本書は写さない——写せば二か所になり、規約を直した日に点検票が古びる。判定は人、材料（該当する節の有無）は機械。失敗機構の節は任意なので、無いことは欠落に数えない。

**点検は、直すことではない。** 材料を出し、裁定の要る項目を並べるところまでが監査であり、本文を直すのは別の作業（内容の改訂＝版上げ・PR）である。この線を越えると、監査が内容に手を入れた分だけ、監査の独立が失われる。

## 6. 監査そのものが壊れる形（失敗機構）

- **機械の門番だけを厚くする。** 通ったことを設計の正しさと取り違える（§1.2）。機械の検査は増やせば増やすほど「通った」の重みが増して見えるが、見ている軸は増えていない。
- **点検票を判定できない項目で埋める。** 「読みやすいか」「適切か」のような項目は、誰にも判定できない。判定者と材料が書けない項目は、点検票に載せない。
- **監査が内容を直し始める。** 直す側と見る側が同じになれば、照合（§1.1）が成立しない。
- **一度きりで終える。** 規約と実装は時間でずれる（§1.6）。回す契機（§4）を決めていない監査は、書いた日にしか効かない。
- **射程を宣言しない。** 対象が数えられなくなり、広すぎて形骸化するか、当たらない文書に当てて硬直する（§0）。

## 7. 未決

- **収録前の材料と、載せた後の材料が別の道具になっている。** `--audit-file`（生の Markdown）と `--audit`（モジュール）で出る項目が揃っていない。どこまで揃えるか。
- 「枠の欠落」は様式の確定待ち（§5）。
- 対象②の材料（影響半径・分割線の検算）は出るようになったが、**まだ実際の裁定に使っていない**。どの数値をどこから疑いとするかは、使ってから決める。
- 種別ごとの点検票——原典・補足・規約・定義書・ランタイムで、掛かる項目が違う。原典（§5）と補足（§5「種別ごとの点検票——補足」・2026/09/23）は立った。規約・定義書・ランタイムは未（§8 の追検証が示すとおり、種別を変えるたびに一度走査して立てる）。
- 文書をまたぐ参照のうち、**節名による参照**は機械で追えない（ファイル名参照は追える）。

## 8. 検証の記録

初版（v0.1）を、README・IDION 原典に加えて、変容理論族 5 本・前提優位・認知フレーム（原典とランタイム）・KOSEI Mining 定義書へ通して当てた（2026-09-12）。**監査そのものの穴が 8 件出た。**

| # | 穴 | 反映 |
| :-- | :-- | :-- |
| F1 | 「1 ファイル＝1 文書＝1 骨格」を暗黙に前提していた（ランタイム文書は、中に生成物の型を持つ） | §2 に場合分けを追加 |
| F2 | 役の二分で収まらない節が実在（警告・対象者・品質規律） | 役を三分へ（`DESIGN.md` §3.2） |
| F3 | 採番の方式が種別ごとに違う | §5 に「採番の一貫性」を追加 |
| F4 | 粒度の物差しが種別で桁違い | §5 を絶対値でなく散らばりで見る形へ |
| F5 | 文書をまたぐ参照が点検票に無い | §2 の対象②と §5 に追加 |
| F6 | 一番必要なとき（収録前）に道具が当たらない | `--audit-file` を実装 |
| F7 | 「枠の欠落」は様式が未確定では判定できない | §5 に依存と保留を明記 |
| F8 | 射程の「これから載せる文書」が特定できない | §0 に判別子を追加 |

**この記録を残すのは、初版が検証を経たことと、何によって直されたかを、次に読む者が再導出せずに辿れるようにするためである。** 検証を経ていない版と、経た版は、同じ v0.1 でも別物になる。

**追検証（2026-09-14）——F2 と同じ穴が、種別を変えて再び出た。** 初版の走査は原典を対象にしていた。補足（IDION 補足 4 本）へ当てたところ、**27 節のうち 6 節が三役に落ちない**。原典について語る節——事例集・分離候補の観察欄・原典へのフィードバック候補——である。処置は F2 と同じ経路で、**役を四分へ**（`DESIGN.md` §3.2 に `canon/`）。

**この再発が示すもの——点検票の走査は、種別を変えるたびに一度回さないと穴が出る。** §7 が「種別ごとの点検票」を未決に置いているのと同じ根である。F2 は原典 2 本で出た穴、今回は補足 4 本で出た穴で、どちらも「役が足りない」という同じ形をしている。規約・定義書・ランタイムは、まだ一度も当てていない。
